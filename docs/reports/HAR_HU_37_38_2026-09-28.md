## Delivered scope

HAR-HU-37 adds named package exports for engine, protocol, client, service and
ACP. The new contract enumerates 425 engine exports, 24 protocol exports,
16 client exports, 15 service exports and 3 ACP exports. Root aliases and their
stable declaration signatures remain unchanged. Shared serialization, result
projection, continuation and CLI option contracts now belong to client/compat
modules, with compatibility bridges at historical source paths.

The architecture gate traverses runtime and erased type dependencies, re-exports,
dynamic imports and require calls. It rejects reverse CLI/Desktop/Code edges,
computed imports, package self-reference bypasses and terminal builtins. The
protocol has a separate browser-target build: source-only browser testing had
missed a Node helper introduced by shared bundle splitting, which is now checked
again against the installed artifact.

HAR-HU-38 adds the independent `packages/code` terminal source, Node build,
manifest, documentation and tests. Code owns `zhivex-code`; the Harness 1.x
package retains `zhx`, `zhivex-harness` and `zhx-acp`. Code imports public Harness
subpaths only. Its 26 named `/code-support` exports retain existing tiers where
applicable and classify new helpers as experimental. SQLite diagnostics return
a read-only projection rather than exposing a database connection.

The root package remains version 1.2.0 during implementation. Code is private,
version 0.1.0-dev.0, requiring `>=1.3.0-0 <2.0.0`: the existing registry 1.2.0
does not contain these APIs. Installed tests stage only the temporary Harness
manifest as 1.3.0-dev.0. This is a local, unpublished candidate, not a release
version change or a promise of a published dependency.

Initial consumer attempts exposed test-harness issues: pnpm required its current
workspace override configuration for the unpublished transitive package, and
Yarn rejected the system-tar-repacked staging archive. The final wrapper uses
Bun package packing on the staged manifest, producing a package-manager-compatible
archive. All four managers were rerun on that same final pair. Temporary paths
are normalized in the committed JSON; hashes and outcomes are unchanged.

The retained JSON report records exact tarball hashes, installed versions,
package-manager versions and checks. The consumer is outside the monorepo;
no relative source imports or contributor symlinks are available. Local
dependency overrides/resolutions bind transitive Harness requests to the same
candidate tarball because it has not been published. This configuration is
reported explicitly and must not be confused with a successful default registry
installation of Code.

The engine fixture runs in separate Node processes: an edit reaches
`waiting_approval` without writing, state is reloaded, the approval resumes the
operation, and the completed file and state are checked. Cancellation is also
persisted. Import guards reject terminal output/input listeners and child-process
effects; installed exports are compared with the contract and the browser
protocol dependency closure is inspected.

CLI proof uses a deterministic Node fetch preload for the provider transport,
while exercising the real installed command, Harness and provider parsing. It
checks a nonempty expected model response as well as successful status. Durable
CLI cancellation is checked by cancelling a pending run, inspecting its state
in another invocation and verifying the unapproved file was never written.
These are deterministic installed tests, not live-provider certification.

## Delivery and limits

The new CI job defines npm, pnpm, Yarn and Bun installation checks on Node
22.13.0 and Node 24, with retained reports. Remote execution is pending; local
evidence above does not claim Linux, minimum Node or remote CI success.
Desktop still uses its existing internal bridges (HAR-HU-39). Full independent
release compatibility, version ranges and upgrade/uninstall orders belong to
HAR-HU-40.

No npm package was published, no name reserved and no credentials changed.
The prior authenticated npm permission check returned E401 and package visibility
check E404; those remain release prerequisites. The prior push rejection also
remains unresolved, so this work is delivered locally until explicit push
authorization is provided. Notion tracks review status and links the local
commit/evidence; it must not claim remote review or completed publication.
