# Muse 1.3: HTTP 400 en continuación OCI

Fuente: main 6839623f7511222c31f26cd133773ff256eb0d3f, Core 1.23.0-next.2, Agents 1.9.0-next.2, Meta 0.2.7-next.0, Muse Spark 1.3 por Responses.

Tras aprobar orquestación Meta/OpenAI y OCI Qwen/OpenAI, OCI Meta falló HTTP 400. Un primer diagnóstico pasó. Una campaña posterior limitada a tres casos se detuvo en el primero: peticiones 1 y 2 HTTP 200, petición 3 HTTP 400. Un segundo diagnóstico de identidad reprodujo el mismo rechazo.

En el segundo fallo, previous_response_id coincide con una respuesta recibida de Meta; el único recibo de continuación coincide con el call_id recibido; todas las llamadas de esa respuesta tienen recibo. No hay duplicados. La falta de un function_call inline es esperada al usar contexto servidor y no demuestra un recibo huérfano. La documentación primaria permite continuar con previous_response_id y enviar sólo el input nuevo: https://dev.meta.ai/docs/protocols/responses.

Esto descarta un desajuste de IDs en este caso, pero no demuestra que todo el payload sea válido ni atribuye aún el defecto al SDK o servicio. El cuerpo no se conserva: sólo flags cerrados (incluye invalid, no schema/tool/call_id), status y contadores. No se agrega retry de HTTP 400, no se cambia el transporte ni se relajan aprobaciones. Publicación detenida; routing y matriz representativa pendientes.

## Reproducción acotada

Con credenciales privadas ya configuradas:

```bash
ZHIVEX_HARNESS_LIVE=1 ZHIVEX_HARNESS_LIVE_FAIL_FAST=1 \
ZHIVEX_HARNESS_LIVE_PROVIDERS=meta \
ZHIVEX_HARNESS_LIVE_META_MODEL=muse-spark-1.3 \
bun run --env-file=.env --preload=./scripts/diagnostics/trace-meta-oci-http.ts \
scripts/live-execution-smoke.ts
```

El preload guarda los identificadores sólo en memoria y emite booleanos de igualdad. No imprime cuerpos, argumentos, headers, IDs ni secretos. Esperar la captura previa puede alterar timing: el fallo también se observó sin instrumentación. El script es diagnóstico, no un adaptador ni una reparación.

Siguiente prueba: aislar un fixture mínimo de continuación con resultados sintéticos y comparar SDK frente a HTTP directo conservando los mismos bytes de solicitud; sólo luego evaluar alternativas documentadas. Registrar todos los casos y detener la serie ante el primer rechazo. No declarar resuelto por controles verdes aislados.
